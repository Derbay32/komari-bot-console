# AGENTS.md

## Project

Komari Bot Console is a Chinese-language administration UI for the Komari bot.
It uses Next.js 16 App Router, React 19, TypeScript, Ant Design 6, and TanStack
Query. Use npm; dependency versions and scripts are defined in `package.json`
and `package-lock.json`.

## Task-specific entry points

Read the files relevant to the change, not every entry below before each edit.

- **Pages and UI:** `src/app/(console)/` contains route wrappers;
  `src/components/` contains feature UI. Follow the affected feature's pattern.
- **Data access:** `src/lib/hooks/` contains React Query queries and mutations;
  `src/lib/http/client.ts` provides `apiFetch` and shared error handling.
- **Backend proxy and credentials:** `src/app/api/proxy/[...path]/route.ts` and
  `src/lib/server/runtime-config.ts` define the server-side boundary.
- **API contracts:** `src/types/komari-api.d.ts` is generated by
  `scripts/sync-openapi.mjs`.
- **Theme and providers:** `src/app/providers.tsx` owns Ant Design's Chinese
  locale, theme integration, and the Query provider; `src/app/globals.css`
  contains shared styles.
- **Framework or build changes:** consult `next.config.ts`, `tsconfig.json`,
  and `eslint.config.mjs`. For environment setup, consult `README.md`.

## Implementation constraints

- Target Next.js 16 App Router APIs. Do not introduce Pages Router code or
  deprecated APIs such as `next/router` and `next/head`. Use current official
  documentation when framework behavior is uncertain, not older examples.
- Keep route wrappers and layouts as Server Components unless they need client
  behavior. Put interaction in Client Components; preserve the existing
  hook-based data flow rather than converting features to Server Actions as
  incidental cleanup.
- Await request-time APIs (`cookies`, `headers`, `draftMode`) and route
  `params`/`searchParams` before access in server code. `typedRoutes` is enabled;
  prefer generated route helpers where applicable.
- Cache Components are not enabled in `next.config.ts`. Keep management API
  requests uncached (`no-store`); do not add shared caching or enable Cache
  Components as a side effect of unrelated work. If explicitly enabling them,
  revisit route segment cache configuration and dynamic rendering boundaries.
- Browser calls to the Komari backend go through `apiFetch` and `/api/proxy`.
  Keep backend bearer tokens and secret loading on the server; do not expose
  them through `NEXT_PUBLIC_*`, client props, or browser requests to upstream.
  New server mutations must validate authentication, authorization, and input.
- Follow the affected hooks' query-key and invalidation conventions. For
  audited mutations, preserve the header encoding in `src/lib/http/audit.ts`;
  it handles Chinese change reasons that cannot be sent as raw header values.
- Use `observePromise` / `observeCallback` from `src/lib/async.ts` only for
  intentionally non-blocking work or void event callbacks. Await work that
  determines success; do not use an observer to hide required sequencing.
  Promise-aware callbacks such as `Popconfirm.onConfirm` must retain their
  returned Promise. `withReportedErrors` logs action failures and preserves
  the result/rejection; a dialog's confirmation result is not its action's
  error channel.
- Do not hand-edit `src/types/komari-api.d.ts`. When the upstream contract
  changes, use `npm run gen:api` and inspect the generated diff. This command
  contacts the configured backend and overwrites generated files; it is not
  a routine validation command.
- Use existing Ant Design components and theme tokens, and keep user-facing
  copy in Chinese. Match nearby TypeScript style and the `@/` source alias;
  do not introduce `any` or `@ts-ignore` to bypass type errors.
- Keep refactoring and migration within the requested scope. Do not introduce
  compatibility layers or unrelated cleanup to complete a focused change.

## Validation and completion

For an implementation task, continue through relevant verification and fixes
for problems introduced by the change, rather than stopping at the first draft.
Choose checks according to the affected behavior:

- `npm run check` runs the PR quality checks: type generation and TypeScript,
  zero-warning lint, and lint-rule regression tests. For focused work, use
  `npm run typecheck`, `npm run lint`, or `npm run test:lint` separately.
- ESLint enforces legacy API restrictions, deprecated symbols, and Promise
  handling. `void` does not handle a rejection; inline ESLint configuration
  and TypeScript suppression directives are prohibited. Any necessary lint
  exception belongs in `eslint.config.mjs`, with a reason and explicit review.
- When changing a lint rule or its configuration, update its valid/invalid
  cases in `tools/eslint/`. Keep generated files, personal configuration, and
  nested worktrees outside the scan; do not exempt handwritten application code.
- `npm run build` when routing, server/client boundaries, configuration, or
  packaging could affect the production build.
- For UI behavior changes, inspect the affected interaction when a suitable
  local environment is available. The proxy uses the configured backend;
  localhost does not guarantee that data is disposable. Confirm the target
  environment before exercising mutations against real data.

The lint regression tests do not replace application behavior tests.
Documentation-only edits need content, reference, and diff checks, not an
application build. Reuse applicable results rather than repeating successful
checks without a new change or unresolved concern.
Report what changed, what was verified, and any remaining blocker. Local
validation is not deployment approval or a substitute for required PR/CI checks.
